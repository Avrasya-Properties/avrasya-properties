# Backend audit and implemented controls
See [deployment/status](BACKEND_DEPLOYMENT.md) for the live activation blocker and first-admin setup.

The original website used static supplier JSON and a fictional localStorage CRM. The review branch adds Supabase Auth and protected staff membership; RLS-scoped contacts/leads/tasks/viewings/inquiries; shared CMS settings; published-only snapshots; safe supplier provenance; optimistic edits; guarded, atomic conversion/publication/deal operations; verified physical-unit links; Storage cover uploads; source review/CMS/staff/lease/maintenance management; append-only server audit events; persistent notification receipts and administrator application-data export.

The inspected project already contained 52 application tables, supplier imports and legacy SECURITY DEFINER RPCs without adequate internal authorization. Those legacy RPCs are revoked by the reviewed migration. Protected helpers live in the unexposed private schema with fixed search paths and explicit execution grants. Staff access also requires a live Auth session. Every application table has RLS; public writes go through a validated, rate-limited Edge Function and service-only RPC.

Limitations are explicit: the live migration was rejected by automatic approval review and remains unapplied; first admin is deferred by the owner; hosted Auth/SMTP, public form deployment, exact allowed origins, Storage transfer verification and unattended reservation scheduler require activation checks. Generic editors do not fabricate payment receipts, commissions or completed transactions. Payment rows are read-only. Production browser restore/reset is disabled.

CI uses isolated PostgreSQL and Supabase-compatible Auth helper definitions copied from the actual project. Browser persistence tests use real PostgREST/SQL authorization with fictional Auth endpoint fixtures. This verifies wiring and persistence without creating live users, sending mail or modifying imported client inventory.
